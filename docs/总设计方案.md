# Vanitas-Harness 总设计方案

> 版本：`v0.4.0` · 快照：2026-10-25
> 本文是**架构与契约的唯一事实源**。运行数据与验证边界见 [项目现状.md](项目现状.md)，操作步骤见 [用户使用手册.md](用户使用手册.md)，交互范式见 [ClaudeCode范式笔记.md](ClaudeCode范式笔记.md)，开发协作规范见仓库根 [AGENTS.md](../AGENTS.md)。

---

## 1. 定位与不可协商约束

单机、单用户、单实例的本地推理套件：把 llama.cpp 的 `llama-server` 包成可配置、可守卫、可交互、可批处理的 CLI。

| 约束 | 决策 | 原因 |
| :--- | :--- | :--- |
| 运行时 | Python ≥ 3.10，主逻辑全 Python | 运维只需一个解释器，Windows 上无需构建 |
| 第三方依赖 | 仅 `prompt_toolkit`（REPL 行编辑/历史），其余标准库 | 依赖面越小，3 个月后越删得掉 |
| 配置驱动 | 模型、端口、上下文、KV 类型只出现在 `config\` | 换模型不改代码，守卫与文档共用同一份事实 |
| 启动入口 | 仓库根 `vanitas.bat`，5 行薄壳 | `.bat` 不承载业务逻辑，跨终端行为一致 |
| 并发 | `-np 1`，一次只跑一个 `llama-server` | 8 GB 显存禁不起双实例；单槽吞吐是已知边界 |
| 工具调用 | 只做 `/exec` 手动触发，不做自动循环 | 安全面可控；任务定义明确排除二期钩子 |

明确**不做**：Web UI、账号/多租户、远程访问、自动 Agent 循环、插件/技能体系、分布式部署。这些不是「以后再说」，而是当前形态的边界。

## 2. 物理拓扑

```text
Vanitas-Harness\
├── vanitas.bat                 # 唯一入口：cd 到根目录后 python -m vanitas %*
├── AGENTS.md                   # 开发范式与协作红线
├── README.md                   # 一页索引
├── bin\                        # llama.cpp CUDA 构建（不入库）
├── models\                     # GGUF 权重（不入库；7B 为 2 分片）
├── config\
│   ├── models.json             # 模型/端口/别名/分片/档位
│   ├── settings.json           # 超时/重试/启动/REPL/工具/翻译
│   └── prompts\                # system_default + task_{chat,translate,code,agent}.md
├── vanitas\                    # CLI 实现
├── tests\                      # 单元测试 + 验收基准 + 运行产物（reports/ 不入库）
└── docs\                       # 本文件、现状、使用手册、范式笔记
```

`bin\`、`models\` 是只读输入：任何流程都不得改名、合并、改写权重或 DLL。运行产物写到用户目录（`~/.vanitas_logs/`、`~/.vanitas_run/`、`~/.vanitas_sessions/`、`~/.vanitas_history`），不污染仓库。

## 3. 运行链路

```text
vanitas.bat
  └─ python -m vanitas
       └─ cli.main(argv)
            ├─ config.load_config()        读 models.json + settings.json + prompts
            ├─ guard.evaluate()            运行时 → 模型 → 收旧实例 → 端口
            ├─ launcher.start()            Popen(bin/llama-server.exe) + 写 pidfile
            ├─ launcher.wait_ready()       /health + /v1/models 别名校验
            └─ 业务分支
                 ├─ repl.run()             交互对话
                 ├─ translate.translate_file()  批量翻译
                 └─ batch.run_batch()      JSONL 批处理
```

一次 `serve` 的时序：

1. 加载并校验配置（失败 → `2`）。
2. 守卫按固定顺序检查（失败 → `3`，stderr 首行 `[GUARD-CODE=N] [GUARD-FATAL] …`）。
3. `subprocess.Popen` 启动 `llama-server.exe`，参数由配置拼装、逐字固定（见 6.2）。
4. 轮询 `/health` 至 `status == "ok"`；进程提前退出则带日志尾部报错。
5. 校验 `/v1/models` 返回的 `id` 与配置 `alias` 一致，防止端口上跑着别的模型。
6. 写 `~/.vanitas_run/<model_id>.json`，返回端点；退出 REPL 不影响后台服务端，`stop` 负责回收。

依赖方向严格单向：`cli → {config, guard, launcher, engine, repl, translate, batch}`；`repl → {config, engine, launcher, prompts, render, session, tools, guard}`；`launcher → {guard, engine, config}`；`engine/guard → {config, errors}`。没有反向依赖，也没有循环引用。

## 4. 模块职责

| 模块 | 职责 | 不做什么 |
| :--- | :--- | :--- |
| `cli.py` | argparse 子命令、退出码映射、UTF-8 标准流 | 不拼 llama 参数、不碰业务状态 |
| `config.py` | 读 JSON、严格校验、dataclass 视图、环境变量覆盖 | 不检查文件是否存在（交给守卫） |
| `guard.py` | 运行时/模型/分片/旧实例/端口检查，退出码 0/1/2/3/4/9 | 不启动服务、不判断显存是否够 |
| `launcher.py` | 进程生命周期、日志、pidfile、`/health` 就绪、停止与状态 | 不决定用哪个模型/档位 |
| `engine.py` | OpenAI 兼容 HTTP、超时、重试退避抖动、SSE | 不渲染、不保存历史 |
| `session.py` | 消息历史、系统提示、任务模板、预算裁剪、存档 | 不发请求 |
| `render.py` | 纯文本流式渲染、代码块缩进 | 不做 ANSI 全屏重绘 |
| `repl.py` | 12 个 `/` 命令、提示符、命令分派、单轮对话 | 不做自动工具循环 |
| `prompts.py` | 模板加载、占位符校验与替换 | 不拼请求体 |
| `tools.py` | `/exec` 白名单、确认、受控执行 | 不做后台任务与自动重试 |
| `translate.py` | txt/md/srt 分段、翻译、重组、失败汇总 | 不管理服务端 |
| `batch.py` | JSONL 解析、逐行执行、结果落盘 | 不重试失败行 |
| `errors.py` | 统一异常类型与 `retryable` 语义 | 不打印、不退出 |

## 5. 配置契约

### 5.1 `config/models.json`

字段名固定；新增模型**只允许追加 `models[]` 条目**，不得改 schema。

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | string | CLI 使用的短名（`serve <id>`、`--model`），唯一 |
| `display` | string | 人类可读名称，只用于展示 |
| `path` | string | 相对仓库根或绝对路径；分片模型必须指向 `-00001-of-0000N` 首片 |
| `port` | int | 默认端口，唯一；`VANITAS_PORT` 可覆盖 |
| `alias` | string | `-a` 参数与 `/v1/models` 的 id，唯一，不带分片后缀 |
| `shards` | int | 分片数；`>1` 时文件名必须与 `path` 的分片模式一致 |
| `role` | string | `general` / `light` / `translate` / `baseline` |
| `template_kwargs` | object | 原样注入 `chat_template_kwargs`（标量值） |
| `profiles` | object | 档位表，键为数字串；每档 `ctx/kv_k/kv_v/desc` |
| `default_profile` | string | 默认档位键 |

校验规则（失败一律 `ConfigError` → 退出码 `2`）：`version == 1`；id/port/alias 唯一；档位键为数字串且默认档位存在；KV 类型在 `f32/f16/bf16/q8_0/q4_0/q4_1/q5_0/q5_1/iq4_nl` 内；分片命名与 `shards` 自洽；`path` 解析为绝对路径；未知字段直接报错（防手误）。

生效优先级：`--profile` > `VANITAS_PROFILE` > `default_profile`；端口：`VANITAS_PORT` > `models[].port`；配置目录：`--config-dir` > `VANITAS_CONFIG_DIR` > `<仓库根>/config`。

### 5.2 `config/settings.json`

| 段 | 字段 | 语义 |
| :--- | :--- | :--- |
| 顶层 | `version` / `host` | 配置版本；监听地址（只允许回环） |
| `request` | `timeout_sec` / `max_retries` / `backoff_base_ms` / `backoff_jitter_ms` | HTTP 读超时、最大重试、退避基数、抖动上限 |
| `launcher` | `health_timeout_sec` / `health_poll_interval_ms` / `kill_wait_sec` | 就绪等待、轮询间隔、停止等待 |
| `repl` | `history_file` / `max_context_tokens` / `stream` | 历史文件、上下文上限、是否流式 |
| `tools` | `exec_enabled` / `exec_whitelist` / `exec_require_confirm` | 工具开关、白名单前缀、逐次确认 |
| `translate` | `source_suffixes` / `chunk_chars` / `output_suffix` | 支持扩展名、分块大小、输出后缀 |

`/exec` 的子进程超时复用 `request.timeout_sec`，不另设字段，避免 schema 漂移。

### 5.3 `config/prompts/`

只认 `{input}`、`{context}`、`{date}`、`{model}` 四个占位符。`task_*.md` 必须含 `{input}`；未知占位符、空模板、路径穿越（`../`、大写名）在启动前报错。`system_default.md` 作为默认系统提示；`/system`、`/task` 可在会话内覆盖。

## 6. 进程、端口与守卫

### 6.1 端口分配

| 模型 | 端口 | 档位（默认） | 用途 |
| :--- | :-: | :--- | :--- |
| `qwen7b` | 4060 | 4K + Q8_0 | 通用主力 |
| `minicpm` | 4061 | 8K + F16 | 轻量 |
| `hymt` | 4062 | 4K + Q8_0 | 翻译 |
| `qwen3b` | 4063 | 8K + Q4_0 | 回归基线 |

不得复用 8080 段（Steam 等桌面进程常占）。单实例：启动新模型前由守卫回收所有 `llama-server.exe`。

### 6.2 启动参数（逐字固定）

```text
llama-server.exe -m <path> --host <host> --port <port> -c <ctx> -ngl 999 -np 1
                 -fa on -ctk <kv_k> -ctv <kv_v> -a <alias> -fit off --metrics
```

`-fa on`、`-fit off`、`-np 1`、`-a`、`--metrics`、分片只传首片都是硬语义，不得在重构中「顺手优化」。

### 6.3 守卫

顺序固定：**运行时（4 个 DLL）→ 模型（存在/分片/体积/GGUF magic）→ 回收旧实例 → 端口**。先验模型再杀旧实例，避免目标不可用时误伤正在服务的实例；端口仍被占则报 PID 与映像名，由操作者决策。

| 退出码 | 含义 | stderr 首行 |
| :-: | :--- | :--- |
| 0 | 通过 | `[GUARD] 环境核验通过…` |
| 1 | 端口被占 | `[GUARD-FATAL] 端口 <port> 被 PID <pid> (<name>) 占用。` |
| 2 | 模型缺失/分片不全/非法 | `[GUARD-FATAL] …`（原因码 `SHARD_ORDER` / `SHARD_MISSING` / `TOO_SMALL` / `BAD_MAGIC`） |
| 3 | 运行时缺失 | `[GUARD-FATAL] 运行时缺失: "…"` |
| 4 | 旧实例未退出 | `[GUARD-FATAL] 存量 llama-server 实例 <n> 秒内未退出…` |
| 9 | 参数错误 | `[GUARD-FATAL] 端口必须是整数…` |

CLI 包装失败时在首行前加 `[GUARD-CODE=N] `，一条消息同时满足两个契约。

## 7. 客户端（engine）

- 只用 `/v1/chat/completions`、`/v1/models`、`/health`；`urllib` 全部走 `ProxyHandler({})`，避免系统代理劫持 `127.0.0.1`。
- 超时：连接与读分别可控，默认 `request.timeout_sec`；健康检查固定短超时、不重试。
- 重试矩阵：连接错误 / 超时 / 5xx 重试；4xx 与协议不合法不重试（`EngineError.retryable=False`）。退避 `base * 2^i + U(0, jitter)`，上限由 `max_retries` 控制。
- 流式：逐行解析 `data:`，`[DONE]` 收尾；首字前失败可重试，已输出后不再重试（避免重复内容）。
- 请求体固定注入 `chat_template_kwargs`（来自模型配置，空对象不注入）；`enable_thinking=false` 对 MiniCPM5 是必需项。
- 指标口径：吞吐只认服务端 `timings` / `usage`；SSE 分片数不是 token，禁止拿来算 t/s。

## 8. 交互契约（REPL）

命令解析：仅「以 `/` 开头且第 2 个字符不是空格」的行视为命令；其余整行都是用户输入。

| 命令 | 参数 | 行为 |
| :--- | :--- | :--- |
| `/help` | — | 由命令表自动生成 |
| `/model` | `[id]` | 无参列出 4 个模型与运行态；带参切换连接，未就绪只提示 `serve` |
| `/profile` | `[N]` | 查看/设置档位，仅对下次 `serve` 生效 |
| `/system` | `[text\|file]` | 设置系统提示；参数是存在的文件则读文件 |
| `/task` | `[name]` | 应用 `task_<name>.md`，每轮输入填入 `{input}` |
| `/clear` | — | 清空消息，保留系统提示与任务 |
| `/save` | `[path]` | 保存会话 JSON（默认 `~/.vanitas_sessions/<时间>.json`） |
| `/load` | `<path>` | 加载会话，恢复模型/档位 |
| `/exec` | `<cmd>` | 白名单 + 逐次确认执行本地命令 |
| `/stop` | — | 停止所有 llama-server |
| `/status` | — | 模型/档位/端口/记录/显存/会话用量 |
| `/quit` | — | 退出（`/exit` 别名） |

- 提示符 `vanitas[<id>:<档位>]> `；TTY 且有 `prompt_toolkit` 时启用历史与行编辑，否则降级 `input()`；非 TTY 的提示符写 stderr，stdout 只留回答。
- 上下文预算：`budget = max(256, min(档位 ctx, repl.max_context_tokens) - 512)`；超预算时从最早的用户/助手对开始丢，并打印裁剪轮数。不实现自动摘要。
- 渲染：增量写 stdout 并 flush；代码围栏内 4 空格缩进，围栏标记不上屏；结束后打印 `[META]`（token 数优先取 `usage`，无则退化为字符数）。

## 9. 翻译与批处理

`.txt` / `.md`：按空行分段，段内超过 `chunk_chars` 时优先在句末标点切，其次空格，最后硬切；段落前后空白原样保留，段间空行数量不变。

`.srt`：按空行分块，校验「序号 + 时间轴」；只翻字幕文本，多行字幕整体一次请求并保留行结构；重排序号、时间轴、空行与换行风格，检测到 BOM 则写回 BOM。

输出：`<原名><output_suffix><原扩展名>`（默认 `a.srt → a.zh.srt`），`--out-dir` 可覆盖；失败段保留原文、继续后续、汇总 `[TRANSLATE-FAIL]` 并返回 `5`。`--jobs > 1` 只并行解析，请求始终串行（服务端 `-np 1`）。

批处理：一行一个 JSON 对象 `{"id","prompt","system"?,"task"?,"max_tokens"?}`；空行跳过，坏行计入失败；结果写 `<input>.out.jsonl`，任意失败返回 `5`。

## 10. 工具执行安全模型

- 默认 `exec_enabled=false`，`/exec` 直接拒绝并给出开启方法。
- 启用后按规范化字符串做前缀白名单匹配；每次执行前 `y/N` 确认（`exec_require_confirm`）。
- 普通程序 `shell=False` + `shlex` 分词：`& | >` 只能作为字面参数，无法串联。
- cmd 内置命令（`echo/dir/type/...`）没有 `.exe`，改走受控 `cmd /c`，并先拒绝 `& | < > ^ %`。
- 子进程超时复用 `request.timeout_sec`；输出按 UTF-8 → 本地代码页 → `mbcs` 顺序解码。
- 不提供自动循环、后台任务队列或二期预留钩子。

## 11. 显存与档位策略

| 模型 / 档位 | 整卡实测 | 余量 | 结论 |
| :--- | ---: | ---: | :--- |
| Qwen 7B · 4K+Q8_0 | 7,175–7,313 MiB | 约 700–900 MiB | 默认可用 |
| Qwen 7B · 8K+Q4_0 | 7,153–7,417 MiB（v0.2 基线） | 约 600–900 MiB | 长文档备选 |
| HY 7B · 4K+Q8_0 | **7,674 MiB** | **约 500 MiB** | 本机最紧，启动前清显存 |
| MiniCPM 2B · 8K+F16 | 4,299–4,312 MiB（v0.2 基线） | 约 3.8 GiB | 余量充足 |
| MiniCPM 2B · 32K+F16 | 5,346 MiB（v0.2 基线） | 约 2.8 GiB | 长文实验 |
| 3B · 8K+Q4_0 | 3,375 MiB（v0.2 基线） | 约 4.7 GiB | 基线 |

降级顺序：先换小模型（MiniCPM/3B），再降档位（8K → 4K、F16 → Q8_0/Q4_0），最后才动 `-ngl`；不要在 `-fit off` 下依赖系统内存回退。桌面底噪不是常数，余量按同一时刻的 `nvidia-smi` 判断。

## 12. 仓库、版本与发布

- `main` 保持可运行；改动走短生命周期分支，`--no-ff` 合并后打 annotated tag。
- 提交信息用 Conventional Commits（中文主题），一次提交只做一件事；删除与替代文件放同一提交，保证一次 revert 可回退。
- `bin\`、`models\`、`tests\reports\` 不入库；**禁止 `git clean -fdx`**（会连权重一起删）。
- 行尾：`*.bat` 固定 UTF-8 无 BOM + CRLF；其余文本 LF（`.gitattributes` 裁决）。
- 发布前必须通过：`python -m py_compile` 全量、`python -m unittest discover -s tests`、静态红线四查（端口硬编码、禁用依赖、bat 承载启动逻辑、敏感文件入库）、一次真实模型冒烟。

## 13. 设计取舍与演进边界

- **为什么 Python 而不是继续堆 bat**：守卫逻辑（分片、netstat、tasklist、JSON）在 bat 里已到可维护性极限；Python 可用标准库表达且可单测。
- **为什么保留 0/1/2/3/4/9 守卫退出码**：已有脚本与验收基准依赖它；CLI 再包装一层 `[GUARD-CODE]`，不破坏既有契约。
- **为什么端口 4060 段**：8080 段长期被桌面进程占用；4060 与显卡型号一致，便于记忆。
- **为什么单实例**：显存余量决定不能并行；单实例也让 `stop`、`status`、pidfile 语义简单。
- **为什么不做自动工具循环**：安全边界与任务定义都不允许；`/exec` 只做「人按一次、命令跑一次」。
- **为什么文档拆成四份 + AGENTS**：把「架构契约 / 运行事实 / 操作步骤 / 协作规范」分开，各自单一职责，避免一份巨型文档同时承担四种角色。
- **演进触发条件**：只有出现明确的性能瓶颈、第二实现或跨团队协作需求时，才考虑抽象；在此之前保持单层、直接调用。

历史说明：v0.2 及更早由 5 个 `.bat` + PowerShell 守卫实现，v0.3 起被本方案取代；旧脚本与旧任务书已删除，重构前的快照提交仍可通过 git 历史追溯。
